# Escape scan report for CI/CD

Scan your staging environment with Escape after every deployment and get a readable security report in your pipeline, without slowing your deployments down.

[Lire en français](README_FR.md)

---

## What it does

`escape_scan_report_mermaid.py` connects your CI/CD to Escape:

1. **Starts an Escape scan** of your application once it's deployed to staging, tagged with the deployed commit.
2. **Waits for the scan**, however long it takes. Scans last from about 15 minutes to more than 8 hours, and the duration can't be predicted, so the script polls Escape every 30 seconds instead of sleeping a fixed time.
3. **Publishes the report** about a minute after the scan ends: a Markdown recap on the pipeline run page, plus the PDF report generated by Escape.

The scan runs in its **own workflow**, started once the deployment has succeeded. Your deployment finishes as usual and never waits for the scan.

```
push / merge on main
  └─► your deployment workflow (e.g. "Deploy to staging")
        └─► Escape scan workflow   ← separate, never blocks the deployment
              1. start an Escape scan of the profile
              2. wait for it (15 min to 8 h+)
              3. publish the report: run summary + Escape PDF
```

The script is a single Python file, standard library only (Python 3.8+). Nothing to install.

### What's in the report

| Section | Content |
|---|---|
| Header | Scan name, links to the scan in Escape and to the PDF report, profile, target, status, date, duration, CI gate result |
| 1. Security posture | Score and grade (A to E), open findings by severity, score trend over the last 20 finished scans |
| 2. Overview | Findings per category, scan configuration (mode, duration, authentication), configuration errors and warnings |
| 3. Compliance: OWASP Top 10 | Table of the [OWASP API Security Top 10 (2023)](https://owasp.org/API-Security/editions/2023/en/0x11-t10/): pass or fail, open findings and highest severity per category, and the findings of each failed category |
| 4. Coverage | Endpoints discovered and reached, responses breakdown, coverage per scanner user |
| 5. Findings | Every open finding with severity, description and remediation, linked to its page in Escape |

Charts are [Mermaid](https://mermaid.js.org) diagrams written as text in the Markdown. GitHub renders them natively, in public and private repositories, with nothing to host. Each chart has a matching table, so the report stays readable where Mermaid isn't rendered.

Severity colours in charts: critical purple, high red, medium yellow, low blue, info light blue.

### Measured timings

On a real run (scan of 1 h 17 min, PDF enabled), the report and the PDF were published **56 seconds** after the scan ended.

| Step after the scan ends | Duration |
|---|---|
| Notice the end of the scan | up to 30 s |
| Fetch findings, OWASP mapping and coverage, while Escape renders the PDF | about 1 to 2 min |
| PDF rendering by Escape | usually under 1 min, up to about 9 min observed, capped at 8 min |
| Uploads and run summary | under 30 s |

The report is out within about 2 minutes in the usual case, and within about 10 minutes in the worst case. If the PDF isn't ready after 8 minutes, the report is published anyway and says "PDF report n/a".

## Requirements

- An Escape account with a **profile** for your staging application. The profile id is the UUID in its URL: `https://app.escape.tech/profiles/<PROFILE_ID>/…`
- An Escape **API key**: *Escape → User settings → API key*
- For the ready-made workflow: **GitHub Actions** with GitHub-hosted or self-hosted runners. For other CI systems, see [Other CI/CD systems](#other-cicd-systems).

## Add it to an existing GitHub Actions pipeline

### 1. Copy two files into your repository

```
your-repo/
├── escape_scan_report_mermaid.py
└── .github/workflows/escape-scan.yml
```

`deploy-staging.yml` in this repository is only a placeholder for the demo — don't copy it, you keep your own deployment workflow.

If you put the script in a sub-folder, update the two `python3 escape_scan_report_mermaid.py` lines in `escape-scan.yml` (steps *Start the Escape scan* and *Wait for the scan, build the report*).

### 2. Connect it to your deployment workflow

At the top of `escape-scan.yml`, put the `name:` of your deployment workflow and the branches to scan:

```yaml
on:
  workflow_run:
    workflows: ["Deploy to staging"]   # ← the name: of your deployment workflow
    types: [completed]
    branches: [main]                   # ← branches whose deployments are scanned
```

The scan only starts when that workflow **succeeds**. A failed deployment doesn't trigger a scan.

GitHub only starts `workflow_run` workflows whose file is on the **default branch**, so merge `escape-scan.yml` there first.

### 3. Add the secret and the variables

In *Settings → Secrets and variables → Actions*, use the **Repository** sections, not *Environment*: the workflow doesn't declare an environment, so it can't read environment secrets.

| Type | Name | Required | Value |
|---|---|---|---|
| Secret | `ESCAPE_API_KEY` | yes | Your Escape API key |
| Variable | `ESCAPE_PROFILE_ID` | yes | The profile to scan |
| Variable | `ESCAPE_ON_RUNNING_SCAN` | no | `keep` (default), `replace` or `replace_and_report`. See [When a scan is already running](#when-a-scan-is-already-running) |
| Variable | `ESCAPE_GENERATE_PDF` | no | `true` (default) or `false`. See [PDF report](#pdf-report) |
| Variable | `ESCAPE_FAIL_ON` | no | `critical`, `high`, `medium`, `low` or `info`. See [Security gate](#security-gate) |

### 4. Check the permissions

The workflow requests `contents: read` and `actions: write`. `actions: write` lets it:

- start a new run of itself when a scan outlasts the 6-hour job limit,
- cancel the run waiting for a scan it replaces,
- delete the previous report artifacts.

If your organization restricts workflow permissions, allow *Read and write permissions* in *Settings → Actions → General → Workflow permissions*.

### 5. Deploy and look at the result

Push or merge to your deployment branch. Once the deployment succeeds, open *Actions → Escape scan → the latest run*:

- the **run summary** shows the full report,
- the **PDF report** link at the top downloads the Escape PDF directly,
- the **Artifacts** section lists `escape-report.pdf` and `escape-report-markdown`.

### Deployment outside GitHub Actions

If GitHub Actions doesn't run your deployment (Argo CD, Jenkins, a cloud console…), remove the `workflow_run` block and start the Escape workflow from your deployment tool, through the GitHub API:

```bash
curl -X POST \
  -H "Authorization: Bearer $GITHUB_TOKEN" \
  -H "Accept: application/vnd.github+json" \
  https://api.github.com/repos/<owner>/<repo>/actions/workflows/escape-scan.yml/dispatches \
  -d '{"ref": "main"}'
```

The token needs the *Actions: write* permission on the repository. The same call accepts the inputs of a manual run, for example `{"ref": "main", "inputs": {"on_running_scan": "replace"}}`.

## Configuration

### Manual runs

*Actions → Escape scan → Run workflow* lets you override the configuration for one run:

| Input | Effect |
|---|---|
| `scan_id` | Wait for this scan and report on it, instead of starting a new one. Useful for a scan started from the Escape UI |
| `start_new_scan` | Checked (default): start a new scan. Unchecked: report on the profile's last scan |
| `on_running_scan` | Overrides `ESCAPE_ON_RUNNING_SCAN` |
| `generate_pdf` | Checked (default): Escape generates the PDF report. Unchecked: no PDF, faster report |
| `profile_id` | Overrides `ESCAPE_PROFILE_ID` |
| `fail_on` | Overrides `ESCAPE_FAIL_ON`. `none` turns the gate off |
| `full` | Don't truncate descriptions and remediations in the findings table |

### When a scan is already running

Escape runs one scan of a profile at a time. When a new deployment arrives while a scan of the same profile is still running, `ESCAPE_ON_RUNNING_SCAN` decides what happens:

| Mode | Running scan | New scan | Reports published |
|---|---|---|---|
| `keep` (default) | continues | not started | The running scan's report, by the run waiting for it. The new run only says "scan not started" |
| `replace` | stopped | started | The new scan's report only. The run waiting for the stopped scan is canceled, so it publishes nothing |
| `replace_and_report` | stopped | started | The stopped scan's **partial** report first, with a "Scan stopped and replaced" banner and its own PDF (`escape-report-stopped.pdf`), then the new scan's report, in the same run |

Choose `keep` when every scan must complete, for example long scans on a branch that deploys often. Choose `replace` when only the latest deployment matters. Choose `replace_and_report` to keep a trace of what the stopped scan had already found.

In both `replace` modes, the workflow stops the scan in Escape, waits until it's canceled, then starts the new one, retrying for about a minute if Escape still holds the profile lock. It finds the run waiting for the old scan by its name, which contains the profile id: `Escape scan · profile <id>`.

A scan started from the Escape UI or by an Escape schedule has no GitHub run waiting for it. With `replace`, it's stopped without a report. With `replace_and_report`, the new run publishes its partial report.

### PDF report

With `ESCAPE_GENERATE_PDF` set to `true` (default), the workflow asks Escape for the same PDF as *Export report* in the Escape UI, downloads it, and attaches it to the run:

- uploaded **as-is, not zipped**, as the `escape-report.pdf` artifact,
- linked from the report header: one click downloads the PDF,
- the report never contains Escape's temporary download link (it expires after 6 hours).

Set it to `false` to skip the PDF. The report is then published in seconds, with no PDF link and no `escape-report.pdf` artifact.

**Only the latest report is kept.** Each run deletes the report artifacts of the previous runs **on the same branch**: a pull request branch doesn't delete the `main` report. Artifacts are kept 90 days when no new run replaces them.

### Security gate

With `ESCAPE_FAIL_ON` set, for example to `high`, the *Escape scan* run turns red when open findings at that severity or above exist. The result is shown at the top of the report and as an annotation on the run. The deployment itself is never blocked: the gate only marks the Escape run as failed.

A scan that ends `FAILED` or `CANCELED` also marks the run as failed. Its partial report is still published.

### Scans longer than 6 hours

A GitHub-hosted job can't run more than 6 hours. The Escape job waits up to **5 h 20 min**, then starts a new *Escape scan* run with the scan id, which resumes the wait, as many times as needed:

| Scan duration | Runs |
|---|---|
| up to 5 h 20 | 1 |
| 8 h | 2 |
| 12 h | 3 |

The last run publishes the report, with the same timings as above. Earlier runs say in their summary that the wait continues in the next run.

Limitations:

- A runner stays busy for the whole scan. GitHub-hosted runners are free on public repositories; on a private repository, an 8-hour scan uses about 8 hours of Actions minutes.
- If the handover fails (GitHub Actions outage, workflow disabled, `actions: write` refused), the scan keeps running in Escape but no report is published. Recover with *Run workflow* and the `scan_id` input.
- On a **self-hosted runner**, a job can run up to 5 days: raise `timeout-minutes` and `WAIT_TIMEOUT` in `escape-scan.yml` and no handover happens.

### Tuning values in `escape-scan.yml`

| Value | Default | Meaning |
|---|---|---|
| `WAIT_TIMEOUT` | `19200` (5 h 20) | Seconds a run waits before handing over to a new run |
| `PDF_TIMEOUT` | `480` (8 min) | Seconds to wait for Escape to render the PDF |
| `timeout-minutes` | `360` | GitHub's job limit on hosted runners |
| `retention-days` | `90` | How long report artifacts are kept |

### Logos

The report header shows two logos, set in `LOGOS` at the top of the script (OWASP on the left, Escape on the right). To show your own logo, replace a URL. The image must be reachable on a **public URL**: GitHub only displays images from public addresses in a run summary, not files from a private repository.

## Script reference

The workflow calls the script, and you can also run it on its own, locally or in another CI.

### Local run

Create a `.env` file next to the script. Never commit it: it's listed in `.gitignore`.

```dotenv
ESCAPE_API_KEY=<YOUR_API_KEY>
ESCAPE_PROFILE_ID=<PROFILE_ID>
```

Values in `.env` override variables already exported in your shell.

```bash
python3 escape_scan_report_mermaid.py                          # report on the profile's last scan
python3 escape_scan_report_mermaid.py --start-scan --wait      # start a scan, wait for it, then report
python3 escape_scan_report_mermaid.py --scan <uuid> --wait     # wait for a given scan, then report
```

The report is written to `escape-report.md`, with the PDF as `escape-report.pdf`.

### Options

| Option | Description |
|---|---|
| `--profile <uuid>` | Profile to scan or report on. Default: `ESCAPE_PROFILE_ID` |
| `--scan <uuid>` | Report on this scan instead of the profile's last scan |
| `--start-scan` | Start a new scan of the profile first, tagged with the CI commit |
| `--start-only` | With `--start-scan`: start the scan and exit, without waiting or reporting |
| `--on-running-scan <mode>` | `keep`, `replace` or `replace_and_report`. Default: `ESCAPE_ON_RUNNING_SCAN`, else `keep` |
| `--stopped-output <path>` | Where to write the stopped scan's report with `replace_and_report`. Default: `escape-report-stopped.md` |
| `--wait` | Wait until the scan is `FINISHED`, `FAILED` or `CANCELED` before building the report |
| `--wait-timeout <s>` | Stop waiting after this many seconds and exit `3`. Default: no limit |
| `--fail-on <severity>` | Exit `1` if an open finding is at or above `critical`, `high`, `medium`, `low` or `info` |
| `--full` | Don't truncate descriptions and remediations |
| `--generate-pdf` / `--no-generate-pdf` | Generate the Escape PDF report or skip it. Default: `ESCAPE_GENERATE_PDF`, else generate |
| `--pdf <path>` | Where to save the PDF. Default: next to the Markdown file, same name |
| `--pdf-timeout <s>` | How long to wait for Escape to render the PDF. Default: `600` |
| `--output <path>` | Markdown file to write. Default: `escape-report.md` next to the script |
| `--stdout` | Also print the Markdown to standard output |
| `--no-step-summary` | Don't append the report to `$GITHUB_STEP_SUMMARY` |

### Environment variables

| Variable | Description |
|---|---|
| `ESCAPE_API_KEY` | Escape API key (required) |
| `ESCAPE_PROFILE_ID` | Profile id (required unless `--profile` is given) |
| `ESCAPE_ON_RUNNING_SCAN` | Same as `--on-running-scan` |
| `ESCAPE_GENERATE_PDF` | `true` or `false`, same as `--generate-pdf` / `--no-generate-pdf` |
| `ESCAPE_PDF_PATH`, `ESCAPE_PDF_TIMEOUT` | Same as `--pdf`, `--pdf-timeout` |
| `ESCAPE_COMMIT_HASH`, `ESCAPE_COMMIT_BRANCH`, `ESCAPE_COMMIT_AUTHOR` | Commit attached to the scan in Escape. Default: the CI commit (`GITHUB_SHA`, `GITHUB_REF_NAME`, `GITHUB_ACTOR`) |
| `ESCAPE_API_URL` | API base URL. Default: `https://public.escape.tech/v3` |

### Exit codes

| Code | Meaning |
|---|---|
| `0` | Report published |
| `1` | `--fail-on` threshold reached |
| `2` | API or usage error: missing key, unknown profile, network… |
| `3` | `--wait-timeout` reached, the scan is still running, no report yet |
| `4` | The scan ended `FAILED` or `CANCELED`. The partial report is published |
| `5` | No scan started: one is already running and the mode is `keep` |

Transient API errors (HTTP 429, 5xx, timeouts) are retried with exponential backoff. While waiting for a scan, an API error never interrupts the wait.

## Other CI/CD systems

The ready-made workflow is for GitHub Actions, and that's the integration we've run end to end. On other systems, call the script directly: the examples below show the pattern, adapt them to your runners.

Two points to plan for:

- **Don't block the deployment.** Run the scan in a job that comes after the deployment and can't fail the deployment, or in a separate pipeline.
- **Job timeout.** The job waits as long as the scan runs. Set your CI's job timeout above your longest scan, or use `--wait-timeout` and re-trigger the job with `--scan <id>` when it exits `3`.

### GitLab CI

```yaml
escape-scan:
  stage: post-deploy          # after your deployment stage
  needs: [deploy-staging]
  allow_failure: true         # the scan never fails the pipeline's deployment
  timeout: 8h                 # must fit within your runners' maximum timeout
  image: python:3.12-slim
  script:
    - python3 escape_scan_report_mermaid.py --start-scan --wait --output escape-report.md
  artifacts:
    when: always
    paths: [escape-report.md, escape-report.pdf]
    expire_in: 90 days
```

Define `ESCAPE_API_KEY` (masked) and `ESCAPE_PROFILE_ID` in *Settings → CI/CD → Variables*. GitLab renders Mermaid in Markdown files, so open `escape-report.md` from the job's artifacts.

### Jenkins

```groovy
stage('Escape scan') {
  environment {
    ESCAPE_API_KEY    = credentials('escape-api-key')
    ESCAPE_PROFILE_ID = '<PROFILE_ID>'
  }
  options { timeout(time: 8, unit: 'HOURS') }
  steps {
    catchError(buildResult: 'SUCCESS', stageResult: 'UNSTABLE') {
      sh 'python3 escape_scan_report_mermaid.py --start-scan --wait --output escape-report.md'
    }
  }
  post {
    always { archiveArtifacts artifacts: 'escape-report.*', allowEmptyArchive: true }
  }
}
```

Run this stage after the deployment, or in a separate job triggered by it, so the deployment doesn't wait for the scan.

## Security notes

- **Repository visibility.** On a public repository, anyone can read the run summary, and anyone signed in to GitHub can download the PDF artifact: findings, vulnerable endpoints and remediations included. Keep the repository private if that's not intended.
- **API key.** Store it as a CI secret, never in the code. The `.env` file is for local runs only and is excluded from Git.
- **Scan mode.** The scan tests your staging application for real. In `read_write` mode, Escape also sends requests that modify data, so scan staging, not production.

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| `ESCAPE_API_KEY is not set`, exit code `2` | The secret is missing or was created under *Environment* instead of *Repository* |
| The Escape workflow never starts | The `workflows:` name doesn't match your deployment workflow's `name:`, the branch isn't listed, or `escape-scan.yml` isn't on the default branch |
| "Escape scan not started" in the summary | A scan of the profile was already running and the mode is `keep`. Its report comes from the run waiting for it |
| *Delete previous reports* fails | Your organization limits workflow permissions: allow *Read and write permissions* |
| "PDF report n/a" | Escape didn't render the PDF within `PDF_TIMEOUT`, or the download failed. The rest of the report is complete |
| A chart shows as code | The viewer doesn't render Mermaid. The table under each chart has the same data |

Questions or feedback: reach out to your Escape contact.
